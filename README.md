# CAA PDF Extractor — database baseline

Generated from the Retool Database schema exports supplied on 2026-10-04.

## Included Retool tables

- case
- clinical_history
- examinations
- family_history
- laboratory
- medications
- radiology
- states

Retool-specific user-management/sample tables are intentionally excluded.

## Added provenance tables

- source_documents
- extraction_runs

## Important compatibility notes

1. Existing Retool enum values are preserved verbatim, including empty-string
   values in `gender_enum_5ac919f3` and `rx_mode_enum_565bcb50`.
2. Sequence-backed integer primary keys from Retool are represented as modern
   PostgreSQL `GENERATED BY DEFAULT AS IDENTITY` columns. This still permits
   explicit IDs when migrating existing data.
3. Existing nullable/default behavior is preserved as closely as possible.
4. Foreign-key indexes were added for `case_id` columns as a performance
   improvement; they were not explicitly present in the supplied constraint export.
5. No patient data are included.

## Windows setup

Create a PostgreSQL database and user, then copy `.env.example` to `.env` and
set the password.

Example SQL run as a PostgreSQL administrator:

```sql
CREATE ROLE caa_user WITH LOGIN PASSWORD 'choose-a-strong-password';
CREATE DATABASE caa_database OWNER caa_user;
```

Python environment (reuse a valid `.venv` if it already exists):

```powershell
cd C:\app\pdf_extractor
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e .
python -c "import caa_pdf_extractor; print(caa_pdf_extractor.__file__)"
python -m pip install -e ".[test]"
python -m pytest
```

Editable installation makes `PYTHONPATH` unnecessary. Put local patient PDFs in
`pdf_db/<patient_id>/`; `PDF_DB_PATH` can select another local root.

The project `.env` is optional. Copy `.env.example` only when creating a new local
configuration; preserve an existing `.env`. Use real local PostgreSQL credentials
in `DATABASE_URL`. OS environment variables take precedence over `.env` for both
application code and Alembic. Model imports do not initialize an engine or require
`DATABASE_URL`; database operations give a clear error if it is absent.

For laptop development set `LLM_BACKEND=mock`. This backend performs no inference
and returns empty extraction lists; use injected fake clients for deterministic
extraction tests. For the home PC set `LLM_BACKEND=granite` and optionally
`GRANITE_MODEL=granite4.2:latest`. An unset backend defaults to Granite to preserve
the existing home-PC behavior. Granite uses the local Ollama runtime described
below. No model/runtime imports are needed for general package imports.

The deterministic suite needs neither PostgreSQL nor Granite:

```powershell

```

check requiring local `pdf_db` and PostgreSQL.

### Laboratory numeric schema and narrow extraction

Apply `python -m alembic upgrade head` before laboratory extraction. Revision
`0002_laboratory_numeric` changes only the six laboratory measurements to
unconstrained PostgreSQL NUMERIC and removes their zero defaults and the
`date_of_exam` default. Existing integers, legitimate zeros, NULLs and dates are
preserved. The original baseline remains intact. Downgrade refuses fractional,
nonfinite or out-of-range values before converting back to INTEGER.

`laboratory_v1` searches only CSF Aβ42, Aβ42/40 ratio, total tau, phospho-tau,
CRP and HbA1c. Its primary parser uses original PDF words and bounding boxes
through PyMuPDF. It verifies the PDF SHA256 against the ingested source, groups
visual rows, identifies analyte/unit cells, and associates all numeric cells
with their geometric columns. Raw numeric strings are parsed directly into
Python Decimal; audit JSON retains decimal strings without binary floats.
Granite is not used to reconstruct tables.

```powershell
python -m caa_pdf_extractor.extraction.laboratory --patient PATIENT_ID --dry-run
```

Each candidate retains exact source tokens, label/value/unit/header bounding
boxes, reconstructed row text and x-coordinate associations. Validation replays
the deterministic extraction against page tokens. Competing labels, values or
date columns block acceptance. Date headers must occupy the value column or a
directly adjacent table-header row; overall ranges and unrelated dates never
supply individual measurement dates. Missing individual dates remain NULL.
First/last/minimum/maximum remain separate candidates even when values repeat;
minimum/maximum summaries remain audit-only.

CRP uses explicit mg/dL and HbA1c explicit percent. Other CRP units and IFCC-only
HbA1c block persistence with UNIT_MISMATCH. When the percent representation is
present, paired IFCC values remain audit-only and create no additional row.
No unit conversions or scaling are performed. CSF source units must be clearly
interpretable and retained in audit; the Aβ42/40 ratio is dimensionless.

Dry-runs create the ignored layout-debug artifact
`data/debug/PATIENT_ID/laboratory_layout_candidates.json`, a successful layout
validation audit, and an immutable VERIFIED artifact under the patient verified
directory. The artifact retains all candidates, with layout provenance
and observation fingerprints for eligible observations. Only CRP in mg/dL and
HbA1c in percent are eligible in the approved persistence convention; IFCC,
minimum/maximum and CSF candidates remain audit-only in this implementation.
Missing individual dates are allowed when source/row/column/value/unit are
unambiguous. The earlier text parser is not the CLI workflow.

```powershell
python -m caa_pdf_extractor.extraction.laboratory --patient PATIENT_ID --commit
```

Commit loads the VERIFIED layout artifact, replays original PDF geometry and
fingerprints, and checks its original successful validation audit without any
Granite call. One observation produces one database row; dates and unrelated
measurement fields are explicitly SQL NULL. Duplicate matching uses case,
date and the populated biomarker/value among active rows. Commit audits record
observation-fingerprint-to-row-ID links. Only a matching linked observation is
safely reused; an unlinked equal-valued row or genuinely distinct equal-valued
NULL-date observations are reported as DUPLICATE_IDENTITY_AMBIGUOUS and blocked.
Other unambiguous observations may commit in the same transaction; blocked
counts are reported explicitly. Existing clinical values are never overwritten.

`test_laboratory_postgres.py` verifies decimal/NULL round-trips and migration
safety using temporary PostgreSQL tables, with no clinical-table inserts.

### Family history

`family_history_v1` selects bounded family-history/kinship passages from prepared
sections and sends those passages to local Granite. It extracts positive family
disease only. Patient diseases, social history, genetic results and negative
family history produce no clinical row. Negative statements remain in audit.
Relative/disease wording is retained from the source; supporting evidence must
be an exact substring after whitespace normalization, with matching document,
section and page metadata and positive family attribution.

The application maps parents, siblings and children to `first grade`, and
grandparents, aunts/uncles, nieces/nephews and grandchildren to `second grade`.
Unspecified familial disease uses NULL relative and `not specified`; other
explicit relatives (including half-siblings without an established convention)
use `unknown`. `Option` is never generated. Conflicting model categories or
uncertain attribution reject validation.

```powershell
python -m caa_pdf_extractor.extraction.family_history --patient PATIENT_ID --dry-run
python -m caa_pdf_extractor.extraction.family_history --patient PATIENT_ID --commit
```

Dry-run writes extraction audits and an immutable VERIFIED artifact under the
ignored `data/debug/PATIENT_ID/verified/` directory; it inserts no family-history
rows. Empty extraction is valid. The complete prepared source is fingerprinted
locally, including unselected passages, so empty artifacts also become stale
when source content changes. Commit revalidates the original successful audit,
source fingerprint, prompt and model, without creating or calling a Granite
client. Missing, stale or altered artifacts block commit.

Patient ID resolves through `case.fallnr` to `family_history.case_id`. Duplicate
identity is case ID plus whitespace-normalized, case-insensitive relative and
disease plus relative category among `deleted=false` rows. NULL matches NULL;
evidence is audit payload. Existing rows are skipped without alteration, and
insertion and commit audit share a transaction protected by a case lock.
`case.family_history` is unchanged. Synchronization can be considered separately
as a derived indicator of active family-history rows; absence of extracted rows
does not establish a clinically negative family history.

Apply the database schema using Alembic:

```powershell
alembic upgrade head
```

Alternative: apply `schema.sql` directly using pgAdmin Query Tool or psql.

## PDF extraction and import

The importer reads PDFs under `pdf_db/<patient_id>/`, writes compact schema 2.0
JSON into `data/parsed/<patient_id>/`, and stores the same payload in PostgreSQL
`source_documents.document_json`. Patient ID and relative path are inside the JSON
`document` object, matching the existing database schema. Each new import adds
an `extraction_runs` provenance record. The connection comes from `DATABASE_URL`
in the project `.env` (the environment variable takes precedence).

```powershell
.venv\Scripts\python.exe -m unittest test_pipeline
.venv\Scripts\python.exe -m caa_pdf_extractor.pdf_ingestion --limit 2 --dry-run
.venv\Scripts\python.exe -m caa_pdf_extractor.pdf_ingestion
```

Use `--pdf-root` and `--parsed-root` to override input/output folders.
`--dry-run` saves JSON without writing to PostgreSQL. Repeated imports skip
existing SHA-256 hashes; legacy rows with a missing JSON payload are repaired.
Identical PDF bytes share one database record under the existing unique hash
constraint. Failed files do not stop the remaining imports, and any failure
produces a nonzero process exit code.

This stage extracts native text, headings and tables; it does not populate the
clinical tables (`case`, `laboratory`, etc.) with interpreted medical fields.
Pages without text are counted and marked `needs_ocr` in the extraction run;
OCR is not currently implemented. Database tables must already exist (apply
`alembic upgrade head` for a new database).

## Patient document preparation

`caa_pdf_extractor.preparation` builds a deterministic, derived patient bundle
from all `source_documents` whose JSON metadata contains the requested
`document.patient_id`. Documents are ordered by source document ID and remain
separate. Preparation performs database reads only; parsed source JSON and
clinical tables are not modified. No LLM or clinical row extraction is involved.

```powershell
.venv\Scripts\python.exe -m unittest test_preparation test_pipeline
.venv\Scripts\python.exe -m caa_pdf_extractor.preparation.patient_bundle 2473679415
```

The command saves `data/prepared/2473679415.json` and prints only patient ID,
document count/types, section counts, candidate target counts, and table count.
Use `--output <path>` for another destination. The Python API is
`build_patient_bundle(patient_id)`; its result supports `.to_dict()`.

Sections use detected headings that can be located as whole lines in the
original text. Unmatched headings are ignored; pages without usable headings
receive page fallback sections. Sections stay within a page, including when
a logical topic continues on the next page. Each section includes patient ID,
source document ID, stable section ID, and page start/end. Concatenating
`source_text` for a page reconstructs the original page exactly.

`text` is the cleaned extraction representation. Only exact normalized contact
or website lines seen in the first/last three nonempty lines of at least three
pages and at least 70% of document pages are excluded. Body occurrences are
retained. Each exclusion records original text, page, line number, and reason
in `excluded_noise`. Repeated clinical headings are retained.

Table rows, including empty cells, are copied unchanged. A unique cell-text
match assigns a table to a section on its page. Without a unique match, the
table is carried by the first section on that page and explicitly marked
`page_fallback`; the parsed source has no table coordinates for a geometric
nearest-section decision. Every table retains its page and source table index.

Document classification requires an explicit report/letter type phrase near
the start or in first-page headings. Conflicting or absent evidence yields
`unknown`. Dates require explicit date labels and valid ISO or day.month.year
values with four-digit years; conflicting dates yield null. Candidate targets
use headings or short opening lines, are routing hints only, and may be empty
or contain multiple tables. These conservative rules deliberately leave
uncertain metadata unset for later extraction.

### Diagnostic procedure preparation

Bundle version 1.1 adds `diagnostic_procedures` under each document while
retaining the original coarse sections. `diagnostic_splitter.py` recognizes
line-leading RTG, CT/CTA and MRI aliases, including multiline composite
headers connected by trailing commas. CTA remains a CT study subtype.
Examination dates come only from valid parenthesized day.month.year dates
inside these headers; absent, invalid or conflicting dates remain null.

Each procedure retains its patient/document ID, stable procedure ID, page
range, studies, original report text and complete original source slice.
Matching study labels optionally split subprocedure results, including empty
results and literal “siehe oben” references. Page fallback sections can
continue a report across pages; a following procedure or named unrelated
section ends it. Original header/footer text remains in procedure source
slices for provenance. This stage performs no clinical interpretation and
routes events only with `candidate_target: "radiology"`.

```powershell
.venv\Scripts\python.exe -m unittest test_diagnostic_splitter test_preparation test_pipeline
.venv\Scripts\python.exe -m caa_pdf_extractor.preparation.patient_bundle 2473679415 --procedures-only
```

`--procedures-only` still saves the full derived bundle but prints only IDs,
modalities, dates, study names and page ranges, without clinical findings.

## Local Granite clinical history extraction

The first extraction stage selects diagnosis/anamnesis/assessment/clinical
summary sections from a freshly built patient bundle. It sends one bounded
request per relevant document to the installed local `granite4.2:latest`
model through Ollama. `GRANITE_MODEL` can select another installed local
Granite model; `GRANITE_BASE_URL` defaults to `http://127.0.0.1:11434` and
accepts numeric loopback addresses only. Proxies, redirects, model downloads,
cloud models and external inference endpoints are disabled. The adapter is
`llm/granite.py`; versioned instructions are in `llm/prompts.py`.
The transport follows the official [Ollama chat API](https://docs.ollama.com/api/chat).

```powershell
.venv\Scripts\python.exe -m unittest test_clinical_extraction test_diagnostic_splitter test_preparation test_pipeline
.venv\Scripts\python.exe -m caa_pdf_extractor.extraction.clinical_history --patient 2473679415 --dry-run
```

Dry-run is also the default when neither mode flag is specified. It calls
Granite and writes audit records to `extraction_runs`, but does not create
cases or clinical history rows. Terminal output includes only structured
diagnosis fields and a technical summary, excluding supporting snippets and
raw model responses. `clinical_history_v1` is the initial prompt version.

Every dry-run also saves a UTF-8, indented debug export at
`data/debug/<patient_id>/clinical_history_<prompt_version>.json`. Repeating
a dry-run with the same prompt version replaces that debug file. The export
contains patient validation status, selected section IDs, decoded
`granite_response`, normalized output and clinical insert count. Individual
`runs` retain the full outer audit metadata, timestamps and validation errors.
For multiple documents, the top-level `granite_response` is an ordered list
of responses; for a single document it is the decoded response itself.
Invalid JSON responses remain strings so failed runs can still be inspected.
Supporting source snippets are included in the local file, not terminal logs.
Database audit responses remain unchanged as their original strings.

Responses must be JSON without commentary or duplicate keys, then pass strict
Pydantic validation, patient/document/section/page checks, supporting quotation
checks and explicit-date checks. Categories must be null. Dates with only a
month/year or year remain null. Conservative deduplication uses patient context,
whitespace/case-normalized disease text and disease date; formal diagnosis
sections take precedence. Differently worded diagnoses remain distinct.
These checks establish structural and source consistency; they do not replace
clinical review of the model's diagnosis/date interpretation.

Each relevant document gets an `extraction_runs` audit row with model digest,
prompt version, timestamps, exact raw response, dry-run context, selected
section IDs, validated normalized output and validation errors. Statuses are
`SUCCESS`, `FAILED_PARSE`, `FAILED_VALIDATION` or `FAILED_MODEL` (`RUNNING`
while inference is in progress). Failed validation of any document prevents
all clinical inserts for that patient attempt. Failure details exclude source
text from terminal logs; raw responses remain in the local audit database.

The explicit write path is `--commit` (`--write` is an alias). Patient IDs
remain strings throughout parsing, preparation and extraction. At the database
insertion boundary, `resolve_case_id(patient_id)` looks up `public.case.fallnr`
and returns the existing internally generated `case.id`. The matched row is locked
through insertion. Zero matches return `CASE_NOT_FOUND`; multiple matches return
`CASE_AMBIGUOUS`. Either resolution failure inserts nothing. The pipeline never creates or updates a case. Validated clinical rows are inserted in one transaction with
case-level locking and deduplication against existing rows. Missing disease,
admission and discharge dates are explicitly SQL NULL, preventing legacy
CURRENT_DATE defaults from inventing dates. Other clinical tables are untouched.


Commit command (requires an existing case whose fallnr is the patient ID):

```powershell
.venv\Scripts\python.exe -m caa_pdf_extractor.extraction.clinical_history --patient 2473679415 --commit
```

Commit output reports patient ID, matched fallnr, resolved internal case ID,
case existence, validated count, new rows and duplicates skipped. Repeat imports compare normalized
text and disease date for that case under a transaction-level advisory lock.
Folder patient IDs remain strings and may exceed the INTEGER range. Internal
case IDs and matching child foreign keys retain their existing INTEGER types
and automatic primary-key generation; no BIGINT migration is needed.

## Identifier-only case bootstrap

`caa_pdf_extractor.case_bootstrap` uses distinct imported patient identifiers
from `source_documents` (the JSON `document.patient_id` in the current schema)
as authoritative `case.fallnr` values. It never rescans folders or calls a model.

```powershell
.venv\Scripts\python.exe -m caa_pdf_extractor.case_bootstrap --dry-run
.venv\Scripts\python.exe -m caa_pdf_extractor.case_bootstrap --commit
```

Use `--patient 2473679415` to restrict either mode to one imported patient.
The Python API is `get_or_create_case_for_patient(patient_id, commit=False)`;
its result includes the generated/existing case ID and `created` flag. Dry-run
never inserts and reports counts only. Commit preserves the unique fallnr
constraint and uses `ON CONFLICT DO NOTHING` to handle concurrent creation.
An existing case is reused without modification. Batch bootstrap preflights
all identifiers and performs inserts in a single transaction.

Before writing, bootstrap inspects the live case schema and stops on required
clinical fields, absent automatic ID generation, or missing fallnr uniqueness.
`id` and the audit `entry_stamp` are generated by PostgreSQL; `fallnr` is supplied.
All other nullable fields are explicitly set to NULL, overriding legacy date,
boolean, numeric and enum defaults. Patient IDs stay strings; internal integer
case IDs and their generation remain unchanged.

The live schema inspected for this project has `case_fallnr_key UNIQUE(fallnr)`;
no schema migration was necessary. A detailed inspection report is saved in
`data/debug/case_schema.md` and `data/debug/case_schema.json`.

## Local medication extraction

Medication extraction uses bounded medication sections and their immediately
adjacent table continuations. Structured rows take precedence over duplicated
page text. The single `medications.medication` field preserves name, strength,
route, schedule and conditional instructions. Table dose cells remain in their
source order (morning, midday, evening, night for the current source format).
Non-drug compression measures are excluded. No full document is sent to Granite.

```powershell
$env:LLM_BACKEND = "granite"
python -m caa_pdf_extractor.extraction.medications --patient 2473679415 --dry-run
python -m caa_pdf_extractor.extraction.medications --patient 2473679415 --commit
```

Dry-run is the default and writes audit/debug records only. The terminal reports
IDs, input counts, validation status and insert/duplicate counts, without
medication or source text. A readable local debug export, including raw model
response and provenance, is saved to
`data/debug/<patient_id>/medications_medications_v1.json`. Repeating either mode
replaces that export; each attempt retains its database audit records.

JSON and strict Pydantic validation enforce patient/document/section/table/page
provenance and exact source quotations. Table medication values must preserve
every nonempty dose cell. Categories use the existing native enum, and stay null
unless a literal allowed category is present in the supporting row/line. Drug
classes are not inferred. Start/stop dates require a complete date explicitly
labelled for that medication; document/admission/discharge dates are never used.
Unknown dates and categories are inserted explicitly as SQL NULL, overriding the
legacy CURRENT_DATE date defaults.

A failed document blocks every medication insertion for the patient attempt.
Raw responses and validation errors remain in `extraction_runs`. Commit resolves
`patient_id -> case.fallnr -> case.id`, creates no case, and inserts atomically
under the existing case lock. Repeat commits skip existing exact medication
regimens after whitespace normalization, comparing both dates and category.
Different strengths or regimens remain separate. No schema migration is needed.

Deterministic medication tests use injected clients and synthetic sources; model
validation enforces source consistency and still needs clinical review of the
interpretation.

## MRI imaging phenotype extraction

The existing `radiology` table represents MRI imaging phenotypes. CT and RTG
procedures remain in preparation and get `SKIPPED_NON_MRI` audit records; they
never write dates or findings to this table. Each MRI diagnostic procedure is
one local model task. The parser and diagnostic splitter remain unchanged.
An extraction boundary excludes unrelated consultation material accidentally
carried after an MRI report. A source saying no MRI report was created yields
no phenotype rows.

```powershell
$env:LLM_BACKEND = "granite"
python -m caa_pdf_extractor.extraction.radiology --patient 2473679415 --dry-run
python -m caa_pdf_extractor.extraction.radiology --patient 2473679415 --commit
```

Dry-run is the default. Both modes retain per-procedure audits and
write readable UTF-8 debug JSON to
`data/debug/<patient_id>/radiology_radiology_v1.json`. Terminal output is limited
to IDs, modality counts, validation and insertion counts. The mock backend
returns no phenotypes and requires no Ollama.

Successful dry-runs also save immutable artifacts in
`data/debug/<patient_id>/verified/radiology_<timestamp>_<id>.json`, marked
`validation_status=VERIFIED`. Each artifact includes case/event provenance,
exact normalized evidence, CAA metadata, model identity, creation time and
SHA256 fingerprints of the source/procedure and actual prompt (including schema
and acuity rule version). Later failed attempts do not overwrite these artifacts.

`--commit` uses the latest verified artifact and **never calls Granite**. It checks
fingerprints, prompt/rule version, configured model name, case resolution and
the original successful inference audit records. The saved raw response is
revalidated against current source text, retaining exact evidence; the original
normalized output is persisted. Commit audits record
`operation=COMMIT_VERIFIED_EXTRACTION`, `inference_performed=false`, artifact hash
and source run IDs. Model digest provenance is checked against those original
audits without contacting Ollama. Missing, stale or invalid artifacts return
`NO_VERIFIED_EXTRACTION`, `VERIFIED_EXTRACTION_STALE` or
`VERIFIED_EXTRACTION_INVALID`; run and review a successful `--dry-run` first.
Verified empty MRI extractions are valid and insert no rows. Clinical rows and
successful commit audit records share one transaction.

Previously reviewed successful debug snapshots can be promoted without
inference using `radiology_artifacts.verify_debug_artifact(patient_id, path)`.
Promotion verifies the snapshot against its original database audits and current
source before creating fingerprints. It does not modify the source or old audits.

`radiology_v1` extracts supported enum phenotypes with concise verbatim evidence.
One MRI can create several rows (for example lobar hemorrhage and cmb). Date,
modality, studies, source document and pages always come from preparation;
conflicting unsolicited model metadata is recorded and reconciled. Only MRI
dates enter `mri_date`; missing dates are explicitly SQL NULL. Acuity is derived
deterministically per phenotype: a currently described macroscopic intracerebral
hematoma/hemorrhage is true unless its source statement establishes old/chronic,
residual, remote/previous hemorrhage or similar non-acute status. CMB and CSS are
false under this database's imaging-marker convention, without requiring the
literal word chronic. Other supported phenotypes remain NULL when their wording
does not establish a defensible classification. Comparison imaging does not
establish lesion chronicity. The original model bool and any reconciliation remain
auditable under `phenotype_specific_v1`; verbatim quotations and provenance are
still mandatory, and CAA suspicion remains audit-only.

Each row uses the resolved internal `case.id`, `pid=patient_id=case.fallnr`,
`deleted=false` and `saved_on_hdd=false`. CAA suspicion, microbleed descriptions,
edema, absent midline shift and other descriptive observations are audit-only;
they do not generate placeholder `other` rows or new database columns.

All intended MRI records must pass JSON, Pydantic and quotation/support checks
before any clinical insertion. Any failed MRI blocks the whole patient commit.
Clinical inserts use one transaction and the existing case advisory lock.
Duplicate keys are case ID, deterministic MRI date, type and acuity among rows
with `deleted=false`; no new audit FK is required. A repeated phenotype on a
different MRI date remains distinct. Raw responses, errors, deterministic event
context, normalized findings and per-event insert/duplicate counts remain in
`extraction_runs`. Debug output is overwritten by subsequent attempts, while
database audit history is retained. Review real dry-run findings against their
source evidence before committing; source checks do not replace clinical review.

## Ancillary diagnostic examination extraction

`examinations` stores instrument-based diagnostic procedures and their results:
ultrasound, amyloid/FDG PET-CT, SPECT, body MRI and other. It does not represent
neurological bedside status, NIHSS, cognition or blood pressure. Existing UI labels
are Type, Location, Result, Neck vessel result and Date. No schema migration is
needed. The ORM neck-vessel enum spellings now match the existing live/baseline
`perc` labels rather than percent-sign spellings.

```powershell
$env:LLM_BACKEND = "granite"
python -m caa_pdf_extractor.extraction.examinations --patient PATIENT_ID --dry-run
python -m caa_pdf_extractor.extraction.examinations --patient PATIENT_ID --commit
```

`examinations_v1` selects explicitly headed, bounded procedure reports within
prepared sections. It separates bilateral duplex reports and stops before
unrelated reports, shared assessment, therapy and laboratory content. Explicit
planned/recommended studies and neurological status sections are excluded.
Recognized headings include neurosonology, carotid/neck-vessel duplex, transcranial
sonography/Doppler, echo, explicit amyloid/FDG PET, SPECT and body MRI. Routine
brain CT/MRI, neurological status, NIHSS/MMSE/MoCA, laboratory and medications
are excluded. Other ancillary examinations are not routed without a clear
schema mapping. Anatomy is determined only when stated or supported by the
named procedure; mixed anatomy fails rather than choosing arbitrarily.
Echocardiography maps to ultrasound/heart; leg duplex maps to ultrasound with
location NULL because this schema has no leg-specific enum. Laterality remains in source/audit context and must be preserved where relevant
in the selected result quotation. Examination dates come only from the procedure
header, never the document/admission/discharge date. Unknown dates are explicitly
SQL NULL, overriding CURRENT_DATE. Neck-vessel categories require explicit current arterial stenosis evidence in a
neck/transcranial ultrasound report. ICA/ACI/carotis interna and MCA/ACM/cerebri
media aliases map by explicit right/left side and a supported >50% severity.
Vague high-grade wording, exactly 50%, >=50%, uncertain ranges, suspected or
negated stenosis never prove >50%. Other clearly stated cerebral vessel stenosis
has its own category. Normal/no stenosis stays NULL, never unknown. Leg vein
thrombosis never supplies these categories. Several applicable categories fail
validation because the target field is scalar. The source-derived reconciliation
is kept in audit metadata under explicit_stenosis_v1.

The model selects a concise contiguous verbatim result quotation. Exact evidence
is retained from that source-validated quote, without paraphrasing. Type, known
anatomy, date and provenance are attached from the focused input; conflicting
model metadata is rejected. Strict JSON/Pydantic validation checks enums, provenance,
metadata and all result text. A failed input prevents verification of the patient
attempt. The mock backend returns empty record lists without Granite.

Debug exports are `data/debug/<patient_id>/examinations_examinations_v1.json`.
Successful dry-runs create immutable VERIFIED artifacts under the patient's
`verified` directory, with examination/source/section metadata, model identity,
exact normalized output and SHA256 fingerprints of input, prompt/schema and
extraction type. Commit checks fingerprints and original audit records and
revalidates retained raw output without a backend or LLM call. Missing/stale/
altered artifacts fail safely. Original inference audits remain unchanged.

Clinical rows and commit audit records share one transaction under the existing
case advisory lock. case_id is the resolved internal case.id; deleted is false.
Primary duplicate identity is case ID, examination date, type, location and
neck-vessel category among rows with deleted=false. Result text is payload and
is never part of that key. NULL values match NULL values. Matching rows are
reused/skipped; their existing result is not overwritten, even when the verified
artifact uses a concise quotation instead of the legacy full report.

Several genuinely distinct examinations may share these fields, especially when
dates or anatomy are unknown. Reconciliation checks the entire patient batch
before writes. Such collisions require unambiguous source/procedure audit links
or explicit examination labels. For legacy reports, only their original label
prefix is used as metadata; body wording is never compared. Matched/inserted row
IDs and reuse reasons are recorded in commit audits, so subsequent payload wording
does not control identity. Unresolved collisions return
AMBIGUOUS_EXAMINATION_IDENTITY with technical details and perform no clinical
writes. The table alone cannot distinguish repeated same-day studies with equal
identity fields; it must not silently merge them. This commit-only identity
change does not alter source/prompt fingerprints or invalidate verified artifacts.
Terminal output contains technical counts and IDs; source/result text stays local
in debug and audit records. Full deterministic tests require neither PostgreSQL
nor Ollama.
